# Pinident project specification

This document records the product behavior and data contract visible in the repository on 2026-10-05. **Implemented** means code exists; the development deployment has separately passed the checks described below, but this does not establish model accuracy. The [README](../README.md) is the operator guide. [IMPLEMENTATION_GUIDE.md](IMPLEMENTATION_GUIDE.md) is the agent handoff.

## Purpose and current scope

Pinident helps a collector mark Pinny Arcade pins in videos and still images, improve pin-area classification from direct reviews, and carry reviewed web crops into a shared training dataset. The Windows editor is a wxPython/OpenCV prototype. The companion is an installable TypeScript web app designed for Cloudflare Workers Static Assets.

The current learned classifier answers **pin versus non-pin for a proposed rectangle**. OpenCV heuristics still propose rectangles. Desktop catalog matching uses image features and reviewed identity crops to suggest a specific pin. A new browser-side reference matcher can provisionally suggest catalog pin names when its local index is available; that index has not been published. No measured detection or identity accuracy, neural object detector, native Android app, or Pinpanion collection-write integration is established.

## Desktop annotation behavior

Desktop proposals are suppressed when they cover more than half of the smaller existing rectangle; slight overlap remains valid. Tracking and catalog results consolidate mostly overlapping observations of the same pin to one saved box per frame, including previously saved frames. A direct review wins over an unreviewed candidate, and the discarded duplicate's feedback crop is removed. Conflicting directly verified identities, deliberate manual names, and wrong-identity reviews are preserved when identity is uncertain.

The entry point `displayvideo.py` opens a video or still image. Videos have frame navigation and playback; an image is a one-frame source. The current frame shows candidate rectangles and a right-side label editor. A click on a rectangle selects it, scrolls its label row into view, and focuses that row's panel; the name field takes text focus when clicked. Ctrl-click and a marquee select multiple visible boxes. Moving and resizing preserve source-image `(x, y, width, height)` coordinates, even with display scaling or rotation.

The Windows entry point writes unexpected Python exception stack traces, including wx callbacks and worker threads, to a rotating log under `%LOCALAPPDATA%\Pinident\pinident.log` so an application error dialog has a diagnostic record.

**Training → Review saved areas...** visits saved non-rejected rectangles in frame order, then hidden rejected areas only after the other areas are exhausted, and displays each source crop without neighbouring rectangles. Newly rejected queued areas also move behind remaining non-rejected work. It shows saved pin/identity state and the highest eligible catalog appearance match, whose percentage is visual match strength rather than a calibrated probability. Actions depend on state: confirm pin presence, confirm or reject a specific identity, choose another catalog pin, mark an automatic area not a pin, or restore one previously rejected area as a positive pin crop. Rejecting an identity in this mode directly confirms that the area is a pin and records a wrong-identity review. **Confirm identity** and Y use the selected catalog result, or one exact catalog name/ID typed in search; with no selection or search they use the saved suggestion. A correction records the old suggestion as a wrong-identity review. N rejects the saved identity outside the search field. Each review uses the normal history path and advances immediately; idle reviews coalesce into background annotation JSON and reviewed-crop SQLite saves. File → Save and normal close wait for pending feedback and save the latest annotations. Skip and previous only navigate. Browsing does not run detection or add new rectangles.
**Pin only** and **Restore as pin** have detailed hover tooltips. Pin only confirms presence without confirming a suggested identity; Restore as pin reverses a prior negative review and clears its old identity guess.

Video decoding uses a shared 128 MiB least-recently-used cache of unrotated RGB frames for the UI and processing worker. After a frame is displayed, a separate capture prefetches up to four following frames on a background thread. The UI, processing worker, and prefetch thread each own their capture; rotation is applied only to the displayed image. Cached frames avoid repeated reads when scrubbing nearby frames, but detection, tracking, and catalog matching still run when requested. A relaxed fallback only catalog-matches newly added boxes after the primary pass.

Moving or resizing an automatic rectangle records its user-corrected bounds relative to the detector proposal. Strong adjacent-frame tracking carries those corrected margins with the object, scaling them when the detected object size changes. It locally fits foreground pixels when a proposal stays too small or too broad, or when a proposal is missed, including fragments entering from any frame edge. An unreviewed automatic rectangle saved on the destination frame can adopt that fit while keeping its existing box object. A destination rectangle that was separately edited, manually drawn, or directly reviewed keeps its own bounds. Corrections remain within each frame's source-image bounds and affect later crop indexing; propagation does not create an independent direct review.

Fresh untracked automatic proposals use the median width and height of directly presence-confirmed, fully visible pins in the same frame as a size reference, even when their specific identities are unknown. Without direct reviews, fully visible inherited observations from confirmed pin tracks supply the reference. When neither exists, at least three similarly sized fully visible observations must form a strict majority before their median becomes the reference. Each full dimension must be between 50% and 150% of the reference. Even when larger boxes vary too much to form that majority, three distinct fully visible boxes each more than twice as wide and high can rule out an isolated tiny automatic proposal. The same strong evidence prevents a saved unconfirmed automatic box from receiving a provisional catalog identity and clears an older provisional suggestion; its rectangle and direct reviews remain. A proposal touching a frame edge may fall below the lower limit along its clipped axis. Tiny corner fragments remain filtered. Primary and relaxed passes use the same rules; tracked observations and verified identities survive them. Physical millimetres alone do not establish image-pixel size.

The frame-number scale above the desktop slider measures labels with the current GUI font, chooses a readable interval for the available width, and updates on resize. It keeps the first and last frame labeled when they fit without overlap.

Desktop close keeps a progress window visible while it stops prefetch, finishes queued workers and an active requested training run, writes the JSON sidecar, and releases the processing reader. Each listed step and the overall close show a percentage and an approximate remaining time. Serialization reports progress by saved frame; stages without internal progress remain at their current percentage until their worker completes. The sidecar is still replaced atomically. A failed close save leaves the editor open and reports the error.

| File → Settings | Shows active annotation, feedback, catalog, classifier, and metadata paths, file status, review counts, classifier freshness, and a persistent Regular/Low detection-resolution choice. Low detects and tracks at a 640-pixel longest side, then returns boxes to source coordinates. Regular is the default. |

A newly drawn manual rectangle asserts that a pin is present, starts with a blank editable identity, stores one direct positive crop, and immediately attempts identity matching. It is not a confirmed specific pin identity until the user verifies a name or catalog ID. A catalog suggestion has a match-strength percentage; this is not a calibrated probability.

The desktop right-pane name field accepts complete free-text names and searches the catalog after a short typing pause. Opening its dropdown keeps the field ready for typing, and a catalog refresh preserves text in progress. Clicking a listed result selects its stable pin ID.

An explicit **Detect Pins** run emits pasteable `PINIDENT_DETECTION` console records sharing one run ID. The worker record lists primary and relaxed proposal `(x, y, width, height)` rectangles in unrotated source-image coordinates after the detector's crop filter. The display record gives source/display/bitmap/panel dimensions, rotation, and bitmap offset. Each final box record includes its source and panel rectangles, existing/new origin, review state, and any provisional identity name, ID, and match strength. This separates proposal errors from display-coordinate errors without saving image content in the log.

The browser scanner emits a `PINIDENT_DETECTION web` console JSON record for a forced paused/photo scan, or for a live scan with at least 15 visible areas at most once every 10 seconds. It includes source and bounded scan sizes, raw candidate proposals, model-rejected, below-match-threshold, and size-filtered proposals, resulting boxes with provisional match strengths, and overlay coordinates/fit in CSS pixels. The reference matcher may suggest a catalog ID/name, but `pin_id` and `name` remain empty until a direct user tag.

Visible rectangle meaning is governed by `review_state`, identity state, and recent identity rejection. Blue is an unidentified, unconfirmed candidate; red is a provisional specific identity on an unconfirmed candidate; orange is confirmed pin presence without a verified identity or a linked observation inherited from a confirmed track; green is a directly presence-confirmed box with a verified specific identity. **Not this pin** and **none of these** clear identity verification and leave a directly presence-confirmed box orange until a new identity is verified, while preserving its positive pin-presence example. Hidden `rejected` observations remain in JSON to suppress repeated automatic proposals.

The single-box context menu offers **Attempt detection** to retry identity matching for that rectangle, **Confirm pin identity** for a specific provisional identity, **Not this pin** to reject the displayed identity and retry, and **Replace with pin** when ranked catalog references exist. A box with a specific identity does not show the generic **Confirm is a pin** item. **Replace with pin** pages show up to 10 distinct choices with score and available `[YEAR/Show]` metadata. The current suggested catalog ID is included in the first page even if it falls outside the colour-and-layout-ranked top ten, so **none of these** can exclude it before retrying. That action records one wrong-ID review for each listed catalog ID. **Not a pin** stays bottommost in context menus and applies only to automatic boxes; it is a direct negative pin-presence review. **Remove area** only removes an annotation and any direct review it owned.

With a multi-selection, **Confirm selected identities** verifies every selected box that has a specific unverified label in one history entry, leaving already verified identities untouched. A mixed selection also offers **Confirm selected as pins** for pin-presence review; choosing identity confirmation leaves unnamed boxes unconfirmed. Pending text edits are committed before either context action so the current label is preserved. `Y` verifies the selected specific identity, `X` rejects one selected identity, `N` marks selected automatic areas as not pins, and `Del` removes the selection when text editing is not active. Ctrl+Z/Ctrl+Shift+Z perform undo/redo. All direct review actions synchronize the feedback database and annotation history.

Frame-level **Contains pin** and **Contains set** assertions remain checked when detector output falls short; the gap remains visible for review. Navigation compares the adjacent frame just left with the destination, even if the destination has saved annotations. Strong appearance/position matching may link tracks and carry verified identity without inventing another direct feedback example. Playback processes one frame at a time on a worker. When adjacent frames change meaningfully, it makes a bounded relaxed search for new edge candidates and attempts catalog identification on those candidates. These remain unconfirmed until reviewed. Scene cuts and long occlusions remain weak points.

## Annotation and feedback data

The media sidecar `<media-stem>.json` maps frame indices to lists of box records and carries `_frame_presence`. Its writer uses a temporary file and replacement for the save. A box uses source-image coordinates plus `tags`, `source`, `track_id`, `review_state`, and optional feedback/identity fields including `feedback_id`, `feedback_label`, `pin_id`, `match_confidence`, `identity_confirmed`, `identity_inferred`, and `identity_rejections`. `prev_box_id` may be present for legacy data but derives from Python object identity and is not a durable cross-load link. The loader tolerates older records without newer fields and creates a UUID track ID where needed.

`bounds_adjustment` is an optional four-number `(dx, dy, dwidth, dheight)` tuple in the sidecar. Absence means detector-owned geometry; a tuple marks user-authored or corrected bounds. `bounds_direct` marks an automatic rectangle edited on that frame; a propagated adjustment leaves it false so a later source correction or undo can update it. The reader accepts older records without these fields, and undo/redo restores them with `coords`.

Reviewed decisions produce feedback examples; Pinpanion stock images enter the SVM directly from the catalog during a training run:

| Decision | Annotation result | Training result |
| --- | --- | --- |
| Draw or confirm a pin | Direct `confirmed` pin-presence observation; identity may be blank. | One positive crop. An unnamed positive still trains pin/non-pin. |
| Verify a specific identity | `identity_confirmed` on that observation. | The positive crop can be a reviewed identity exemplar. |
| Not a pin on automatic box | Hidden `rejected` observation, with original coordinates and suggestion retained. | One negative crop without a true pin identity; previous direct positive on that automatic track is withdrawn. |
| Not this pin | Box and presence review remain; chosen identity is excluded and a new match is attempted. | One wrong-identity crop for that ID/name, separate from pin/non-pin crops. |
| none of these | Each distinct displayed ID is excluded; matching retries. | Up to 10 separate wrong-identity records per full page for the one rectangle. |
| Remove area | Current annotation is deleted. | Any direct example owned by it is removed; no new negative crop. |
| Inherited pin observation | Linked state without a direct review. | One positive crop per saved frame and confirmed track during training indexing; no new direct review. |
| Propagated rejection or wrong-ID review | Linked copy of one decision. | No additional negative or wrong-ID crop. |

`detection_feedback.sqlite3` stores RGB PNG crops, stable example IDs, provenance, and separate wrong-identity reviews. Provenance includes source media/frame/coordinates/track and rights status. **Add to training data** compares direct reviews and saved inherited pin views to stored metadata by stable ID, decodes only new or changed crops, removes absent source examples, and reports pin, linked-frame, non-pin, and wrong-ID totals. A linked view is eligible only while its track has a direct positive review and no rejection; unconfirmed proposals and orphaned inherited boxes are excluded. Each source/frame/track has a distinct linked sample even if adjacent pixels happen to match. An unchanged session does not decode frames or bump the ranker revision. Stored rows and usable visual descriptors are distinct counts; low-detail crops may not influence matching or training. Undo, redo, and annotation import reconcile direct examples; **Add to training data** reconciles linked samples before fitting the SVM. Raw media, generated labels, local SQLite files, and trained model files are ignored data rather than source artifacts.

The catalog SQLite database stores Pinpanion IDs, names, metadata, reference images, and provenance. The desktop imports unseen public feed entries in the background. ORB/FLANN matching attaches a catalog ID when geometry is strong; the conservative appearance fallback can suggest an ID when geometry is inconclusive. **Run training now** reads the stored stock images directly from this database. Each usable image supplies one positive pin feature; the pin ID, original Pinpanion name as an explicit tag, image URL, and rights status are retained in model metadata. Extra local references and catalog metadata rows without an image are not stock training images. Reference rights are recorded as unverified; a public URL does not grant publication rights.

The desktop matcher uses a 12-table LSH descriptor index without multi-probe expansion for large catalogs. This limits the per-crop shortlist lookup cost during frame processing. Strong ORB geometry takes priority. If geometry is inconclusive, the desktop compares stock-image colour and coarse spatial layout across quarter turns. An ordinary unconfirmed candidate receives a name only when the leading distinct pin is visually strong and clearly ahead; a new scan clears an older unverified guess if both catalog and reviewed-crop matching abstain. An area confirmed as a pin, inherited from a confirmed pin track, or carrying a direct wrong-identity review instead receives the highest ranked eligible catalog identity when stronger checks abstain. **Not this pin** excludes the rejected identity and retries that area's crop for a different suggestion. This remains an unverified suggestion with a visual match-strength score. With no eligible reference it stays unnamed. The manual replacement list remains available with combined appearance scores. Real-video identity accuracy remains unmeasured.

## Model and training contract

After a successful training save, `ScrubberFrame` installs the resulting classifier in its live feedback model and invalidates detector work submitted with an older snapshot. All subsequent desktop detection jobs use the new classifier without an application restart. A cloud model refresh records its version and cache but leaves a current locally trained classifier active.

The first desktop fit builds an OpenCV linear SVM from the complete stored crop set. Later **Run training now** calls continue its saved decision plane when reviews or stock images have only been added, and rehearse retained examples from prior media. Model metadata records per-example fingerprints so unchanged runs keep the same weights. A changed or removed input causes a full fit from the current stored set, removing the superseded input's influence. Older saved models without fingerprints get one full fit before they can be continued. The feedback SQLite database remains the durable cross-media source of reviewed crops; the model file and adjacent metadata must travel together to continue the same weights.

`detection_feedback.py` supplies a conservative nearest-neighbour baseline for proposal ranking and identity exemplars. Direct reviews, undo/redo, and import refresh its in-memory vectors. Versioned crop descriptors are stored with reviews and loaded on a background worker at startup; legacy rows are upgraded in batches, with status progress visible while loading. `trained_detection_model.py` is the working saved OpenCV linear SVM trainer for pin/non-pin crop classification. It combines all usable indexed positive and negative review crops with usable Pinpanion stock images as positive examples; at least one usable positive and one reviewed negative are required. The local catalog is read on the training worker, without writing those images into the feedback database. The SVM uses balanced class weights, saves `<database-stem>.svm.yml` with adjacent `.svm.yml.json` metadata, and loads on startup. Metadata records feature version, combined training digest, counts, stock pin IDs, original-name tags, source URLs, and rights status. Settings and training status distinguish stored from usable stock images. A catalog or review change makes the saved model stale; the stale saved classifier remains usable for proposal ranking until retraining, and Settings reports its freshness. A classifier downranks **new detector proposals** predicted non-pin without removing them solely from its binary prediction; reviewed negative exemplars may still suppress strong matches. It does not find rectangles or determine a catalog identity. The old `OpenCVBoxTrainer.py` wrapper is disconnected and incomplete.

The new portable web model uses RGB feature version 2, a linear weight vector and bias, training digest, and sample counts. Python and TypeScript must calculate equivalent features and reject unsupported versions. `export_mobile_model.py` can create an ignored static `mobile_web/model.json` fallback. The browser fetches `/model.json` without relying solely on shell cache and checks at launch, on return, on network reconnect, and roughly every five minutes while open. The browser applies the pin/non-pin model only to new candidate proposals. Desktop detection uses its prediction as ordering evidence because clean stock artwork does not reliably represent video backgrounds. A local offline copy or static fallback may be older than the server version until connectivity returns.

## Shared web training and model delivery

Photo and video previews use the loaded frame's aspect ratio inside a height-capped stage. The media is contained rather than cropped, and overlay rendering plus pointer mapping use the same contain-fit transform. A portrait photo's bottom edge must remain visible and annotatable; letterbox margins do not count as source-image coordinates.

During live camera or recorded-video scanning, **Pause to annotate frame** and **OK — Save and finish** replace the four source choices in the top action row. Candidate actions and annotation tools stay hidden until the frame is paused. Pause keeps the camera or video source available for Resume video; OK saves the latest bounded frame before stopping the source. Source choices return when the scan is finished or stopped.

The web Scan view offers **OK — Save and finish** while a scanned frame is available. It commits the bounded image and all current boxes through the same saved-annotation path, queues D1 sync, stops the media source, and clears the scan state and result cards. It waits for local persistence before closing; failure leaves the frame available. **Stop without saving** discards unsaved changes. Finishing a recorded video uses the time of the scanned snapshot, even if playback moved afterward.

On a paused web frame, **Select or draw** is the default: a drag selects existing visible rectangles covered by strictly more than half their own area; when none qualify, it draws a new manual rectangle. **Draw area** forces drawing even over existing boxes, and **Select areas** forces selection, including an empty result. Tapping a rectangle still toggles its selection.

The browser's heuristic proposal stage accepts connected silhouettes covering most of a close-up frame and drops smaller detail proposals substantially contained in a larger area. This still needs real-camera evaluation on varied backgrounds.

The local web scanner implementation can compare each proposal with an 8×8 normalized visual reference index generated from stored Pinpanion images by `build_identity_index.py`. Its score is a relative visual match strength, not a calibrated confidence or measured accuracy. Fresh automatic boxes require at least 50% match strength; the strongest qualifying proposal sets the width/height reference, and other new untracked boxes must be within 50%–150% of each dimension, allowing a clipped-edge lower bound. If a stronger match appears later in the search, it becomes the reference. The proposed name and percentage appear on the overlay and result card; the suggestion is never direct identity confirmation. Reviewed catalog tags and not-pin decisions add up to 200 local positive and negative visual examples each, used for later matching only on that browser. Manual boxes and previously tracked reviews bypass the new-proposal gate.

The generated index includes source and rights provenance for each reference. All 1,814 current stock images remain marked `source terms unverified`, so only the ignored local preview index can be built; the normal deploy commands require a rights-cleared index and currently stop before upload. The matcher has not been deployed or tested on real phone footage. The binary SVM remains separate and cannot name a pin.

The web app scans camera, photo, or video input on device. A paused frame can be annotated and saved. On the paused image, tapping a visible rectangle toggles its selection. **Select areas** changes drags into a marquee that replaces the selection with every visible rectangle whose own area is covered by strictly more than 50%; **Draw area** changes drags back to adding a manual pin area. **Delete area** or **Delete areas** removes selected boxes from the current annotation without creating a non-pin review; saving the same paused frame again updates its stable annotation ID so desktop sync removes crops from boxes that were deleted. **Review areas for training** creates direct crop classifications: `not_pin`, `pin_unknown`, or `pin_identified` with a selected catalog ID/name. **Unknown** is a separate difficulty decision for a crop too close or unclear to classify; it makes no pin/non-pin assertion and leaves the scan box untouched. The browser keeps its image locally, shares only a bounded 36-value visual signature, and sorts similar future crops behind clearer candidates while still allowing them to be reviewed. A saved review first persists in browser IndexedDB, then automatically POSTs its bounded image and label to the same-origin Worker. A saved frame annotation likewise persists locally and uploads the bounded frame image and all box states. Offline submissions retry by stable ID on reconnect. The desktop imports each confirmed or inherited pin box as a distinct positive crop; unconfirmed and rejected boxes provide annotation context but do not become training examples. Collection records stay in the browser. Collection data is localStorage; cached catalog metadata and reviews are IndexedDB. Source and rights status travel with each uploaded record; current rights status is `unverified`.

Web catalog selection keeps the last five unique known pin IDs in browser localStorage. With no search text, the frame tag dialog and training **Other pin** dropdown show **Recents** first, then a divider and remaining catalog pins without duplicates. The dialog still applies year, category, set, event, and group filters to both sections. Search text replaces this grouping with normal matching results. Selecting a known pin for a frame, training correction, or library addition refreshes the recent order; local unknown IDs and catalog IDs no longer available are not offered as recent choices.

The Worker uses Cloudflare D1 tables `training_events`, `difficulty_marks`, and `model_versions`. Difficulty marks use idempotent same-origin `POST /api/difficulty-marks` and a public bounded `GET` of recent signatures; they do not enter the desktop training revision stream. The browser may POST direct reviews and frame annotations to `/api/training-reviews`; the Worker validates payload shape and bounded image size, and an identical repeat with the same record ID is idempotent. D1 stores the image content in each event payload. An authorized desktop reads incremental revisions from `GET /api/training-reviews?after=<revision>` (paged), using the bearer `PINIDENT_SYNC_TOKEN`. The desktop records the last consumed server revision in local SQLite and upserts by stable example ID, so it need not redownload all events. Each saved confirmed/inherited frame box has its own stable crop ID, including multiple views of the same tracked pin. The token is a Worker secret named `SYNC_TOKEN` and a desktop environment variable; it must never be placed in frontend code or committed. The default desktop server is `https://id.pinpanion.com`; `PINIDENT_SYNC_URL` can select the development endpoint.

After local training, the authorized desktop publishes the portable decision plane with a version-checked `PUT /api/model` only when its stock-image provenance has no unverified rights. A model trained on the current Pinpanion stock imports is saved and used locally, while web publication is held with a visible status because those records say `source terms unverified`. A conflicting base version returns 409 rather than silently replacing a newer model. Public `GET /model.json` serves the latest D1 model or the static asset fallback. Desktop sync runs at startup and every five minutes to fetch the latest model; authenticated sync also imports new reviews. Cloudflare itself stores events and model versions; it does not fit the classifier. Failed network operations should leave local annotations and model usable, with a visible sync status.

`mobile_web/wrangler.jsonc` configures separate production and development Workers, D1 bindings, and custom domains: `id.pinpanion.com` and `id.dev.pinpanion.com`. On 2026-10-04 the development Worker was deployed with its migrated D1 database and `SYNC_TOKEN`; its custom-domain certificate became active, and HTTPS checks passed for the app shell, catalog, missing-model response, and authenticated model status. The additive difficulty-mark migration and updated Worker were deployed later that day; the page, public difficulty GET route, and refreshed service worker returned HTTP 200. The later frame-annotation sync, rectangle selection, and recent-pin picker deployments also passed HTTPS checks; the 390 px and 1280 px layouts had no horizontal overflow, and the live dialog showed Recents first with normal searched results. A synthetic empty annotation POST persisted its embedded image in D1; that smoke row was removed. A real phone upload remains unverified. The desktop also fetched the empty review page through that hostname. No model has been published (version 0), and no real review-to-model publication has been exercised. Production remains undeployed. Public same-origin review submissions need operational rate limiting and monitoring before broad public use. The Worker proxies the public Pinpanion feed at `/catalog.json`; it has no verified authenticated Pinpanion collection-write API.
