# Pinident agent guide

## Purpose and current scope

Pinident aims to identify Pinny Arcade pins in bulk, starting with a Windows tool for annotating pins across video frames. Future goals include a reproducible training dataset and model, identification from images or video, collection records, and an Android scanning workflow that can connect to Pinpanion or PinnyPals. Treat these as goals, not existing features.

This repository is currently a Python wxPython/OpenCV prototype with a TypeScript mobile web companion. `displayvideo.py` opens a video chooser. `videoscrubber.py` reads frames; `scrubberframe.py` coordinates navigation, annotation, and JSON persistence; `pin_detection.py` proposes candidate boxes and conservatively associates nearby frames. `mobile_web/` builds a Cloudflare-hosted installable web app with on-device candidate detection, tracking, and collection storage. `mobile_scan.py` and `mobile_server.py` remain as a legacy Python service but are no longer used by the web app. `controls/` renders and edits Windows boxes, and `events/` defines wx events. `imagescrubber.py` and `displayframe.py` are separate image-viewing prototypes. `OpenCVBoxTrainer.py` is an incomplete experimental wrapper, not a working model-training pipeline. See `README.md` for the current user flow.

`frame_processing.py` runs playback, GUI button detection, and manual navigation detection on one worker. It receives snapshots of annotation boxes and feedback vectors, reads from a worker-only video capture, and returns results for `ScrubberFrame` to commit on the wx thread. The GUI commit must also update existing `inherited` boxes whose identity was still unverified; otherwise playback discards an adjacent verified identity even though the worker linked it. Keep those boxes inherited, and do not create a second direct feedback example. Next and Previous button clicks must update the visible frame index immediately; either direction can analyze an unchecked frame on the worker using the frame just left as its tracking reference. Rapid navigation invalidates older worker results. Saved-chain reconciliation on manual navigation also uses this worker, a box snapshot, and cancellation/revision checks before committing to the original box objects. Do not access wx widgets, the UI video capture, or the SQLite feedback connection from the worker. Pausing invalidates outstanding results. Play uses a one-shot timer and submits the next frame only after the last result is displayed; do not put the saved-chain reconciliation loop back into each playback result callback. `VideoScrubber` caches repeated frames and reads adjacent frames sequentially; keep the UI and worker capture states separate.

## Before changing code

- Read the relevant modules and tests, and check `git status --short` before editing. Preserve user data and unrelated changes.
- Confirm the intended behavior from code or a user decision when an operation could alter annotation data. Do not infer a finished architecture from prototype names.
- Use small, reviewable changes. When a feature crosses GUI, annotation data, and persistence boundaries, define the data behavior first and test it independently of wx where possible.
- Do not introduce a framework, remote service, model, scraper, Android stack, or new on-disk schema merely to prepare for future work. Record alternatives for planning when the choice is still open.

## Annotation and data invariants

- `BoxData.coords` is an `(x, y, width, height)` tuple. Check image bounds and positive width/height at boundaries; distinguish source-image coordinates from scaled or rotated display coordinates.
- Frame annotations are currently saved as JSON beside the selected video (`<video-stem>.json`). JSON maps frame indices to lists of boxes with `coords`, `tags`, `source`, and optional `prev_box_id`. Existing files may omit `source` and `prev_box_id`; preserve compatibility when changing readers or writers.
- `BoxData.id` comes from Python object identity, so `prev_box_id` is a legacy, non-durable link. New annotations carry a UUID `track_id` across matched frames; the JSON reader generates one for legacy boxes that lack it. Preserve this field on save/load and do not assume old links can be reconstructed.
- `BoxData.review_state` is `unconfirmed`, `inherited`, `confirmed`, or internal `rejected`. A user pin-presence confirmation is the only direct green state; other boxes on the same associated track are orange. `identity_confirmed` separately marks a specific name/ID as authoritative; pin-presence confirmation alone must not set it. A newly drawn manual box starts as a directly confirmed pin with a blank editable name and a positive feedback crop; `unknown-#` placeholders cannot be confirmed as identities. **Remove area** deletes only the current annotation and never creates a negative example. **Not a pin** on an automatic area retains a hidden `rejected` observation in the JSON sidecar, creates one direct negative example, and suppresses automatic observations on that track and visually matching unreviewed adjacent boxes; a prior positive review on the same automatic track is withdrawn. Preserve manual annotations and separately confirmed tracks during visual reconciliation. Both context menu and label-row actions must update the frame owner's box list before persistence. The image and tag panels must exclude rejected boxes from interaction while retaining them in the frame list for matching. Catalog matching may improve a provisional automatic suggestion or identify a directly presence-confirmed automatic box; it skips verified identities, inherited tracks, rejected boxes, and manually entered names.
- `feedback_id` and `feedback_label` on a box mark a direct user decision. Confirmation is positive; explicit **Not a pin** on an automatic area is negative. Keep rejected observations in the frame JSON with their coordinates, original suggested tags/`pin_id`/score, and track ID; hide them through `review_state`, not deletion or clearing their provenance. A negative crop has no true pin identity in the feedback database, even if the rejected box retains a false catalog suggestion. Propagated orange and rejected observations must not become duplicate training examples. **Remove area** is not a non-pin label; it removes that observation and its prior positive example if present. `detection_feedback.py` keeps reviewed RGB crops and provenance in the ignored local SQLite database, and its conservative nearest-neighbour ranker filters/ranks new detector proposals. Undo/redo and annotation load must keep the database in sync. Do not claim neural training or measured accuracy from this feedback baseline.
- **Not this pin** rejects a specific identity while preserving the box and its pin-presence review. `identity_rejections` stores immutable direct reviews with ID/name, original rectangle, and frame; the feedback database stores the corresponding wrong-identity crop separately from pin/non-pin examples. Exclude reviewed IDs/names from catalog matches on that tracked object, clear the visible wrong suggestion, and retry catalog matching. Copy exclusions when tracking to a new frame; never count propagated copies as independent training crops. Undo, redo, and JSON load must synchronize these reviews. This is a matcher exclusion and retained training evidence, not a trained identity classifier.
- The right-pane **Feedback model...** dialog and frame status bar show stored versus usable positive/negative crops and feedback revision. `FeedbackModel.refresh` rebuilds vectors immediately after review, undo, and redo; `reload` handles annotation import. Worker jobs receive a stable snapshot with that revision. Preserve the distinction between saved crops and usable descriptors. Per-detection feedback logs include proposal, suppression, and unscored counts. Suppression requires a strong negative match that exceeds the best positive match, so a few rejected card elements cannot rule out every kind of background noise.
- Frame-level user assertions live in `_frame_presence` in the existing annotation JSON. `frame_presence.py` derives checkbox states from those assertions and marked pins: confirmed, inherited, catalog-identified, or explicitly named boxes count; blue proposals and rejected boxes do not. **Contains pin** asserts at least one, **Contains set** at least two. Checking when the marked count is short starts worker detection and a relaxed contrast-normalized fallback. Keep an unmet user assertion checked so a missed pin remains visible. Removing the last marked pin clears the assertions; undo/redo restores them with box changes.
- An explicit **Detect Pins** run and manual navigation to an unprocessed frame use the relaxed search if the primary pass leaves no visible candidates, even without a frame-presence assertion. Explicit Detect Pins also runs best-effort catalog suggestions on existing unverified candidate and pin-presence-confirmed boxes; commit those scores and IDs to the original boxes while preserving directly confirmed identities. Playback and ordinary navigation retain conservative catalog matching. Playback does not run the relaxed fallback on every empty frame, to avoid flooding videos with backing-card proposals. A manually revisited empty frame that Play processed gets one full pass. The status bar reports primary/fallback counts. Keep the fallback on the worker and keep its outputs as review candidates, never confirmed pins.
- Saved unconfirmed boxes can be reconciled with identified, confirmed, or rejected observations through contiguous adjacent-frame chains when both overlap and appearance are strong. Previous and Next navigation pass the frame just left as an explicit adjacent reference, even when the destination was processed before. A strong local template match may add a tracked observation to an empty saved frame; keep it inherited or unconfirmed according to the source, never directly confirmed. Manual navigation checks on the worker; playback only matches the adjacent frame in its worker to keep wx responsive. Cancel an obsolete scan on navigation, editing, or Play; never decode the chain with the UI capture. Preserve the existing target box object and its coordinates. A confirmed identity may replace a provisional catalog `pin_id`; a user-entered name can inherit that identity only when the names match, while a blank manual box may accept it after strong visual matching. Rejection may merge separate unconfirmed automatic tracks and hide their observations in both directions, but must not overwrite manual or confirmed tracks. Propagated rejections are not additional negative feedback examples. Include asynchronously reconciled rejection changes in the originating removal's undo entry. Propagate identity to blank boxes on the same track, but do not mark them directly confirmed without a user action.
- An orange `inherited` box is backed by a confirmed pin-presence observation on its track. Treat its identity as authoritative for subsequent adjacent matches only when `identity_confirmed` is true; presence-only confirmation may link tracks but must leave conflicting provisional names unresolved. Never overwrite a direct user-confirmed identity or label. Skip the catalog matcher on boxes that already inherited an identity. Automatic detections use the conservative ORB matcher; directly confirmed manual boxes use its best-effort suggestion path, which falls back to colour-histogram similarity when ORB cannot distinguish a pin. `match_confidence` is the method's match-strength score, not a calibrated probability; retain it through unconfirmed tracking, clear it with `identity_confirmed` when the user edits the name, and include both fields in save/load and undo history.
- When appearance tracking misses an adjacent box, a strong independent catalog suggestion for the same identity plus substantial box overlap can inherit a verified identity. Require a directly confirmed or trusted inherited source, an automatic unconfirmed target, a catalog score of at least 0.60, and IoU of at least 0.55. Leave distant matches, conflicting IDs, presence-only confirmations, and user-labelled targets alone. Use this after catalog matching on worker jobs and on saved adjacent frames; the resulting orange state is inherited, not a new direct user confirmation.
- A direct pin-presence confirmation can inherit a specific identity only after an adjacent saved-box visual match to a verified identity. Mark that result with `identity_inferred`; it remains green for presence, but it is not an independent identity authority. Recompute it from a direct verified source after changes and persist the flag through JSON and undo history. The right-pane editable catalog picker writes both the canonical pin name and stable `pin_id`; free text clears the ID and match score.
- A user may directly confirm the same tracked pin in several adjacent frames. Each direct review stays green and keeps its own feedback crop; linking tracks must preserve all direct presence and identity decisions. Confirming an inherited box in the current frame promotes only that observation to direct confirmation. Visual matching may join independently confirmed adjacent observations when their verified identities agree; conflicting direct pin IDs stay separate.
- **Add to training data** compares current-session direct positive/negative and wrong-identity reviews with stored metadata by stable example ID. Each distinct rejected catalog ID in a **none of these** page is one wrong-identity example; propagated copies with the same review ID count once. Decode and save only new or changed crops; delete absent source examples. Call `FeedbackModel.refresh` only for affected positive/negative IDs because its current proposal ranker cannot learn identities. An unchanged session should not decode frames or bump the model revision. Frame reads run on the worker with progress and ETA callbacks; SQLite and wx updates stay on the UI thread. Report wrong-identity counts separately from pin/non-pin counts. This action indexes identity training evidence but does not train an identity classifier or neural model.
- Undo and redo history belongs to `ScrubberFrame` and is keyed by frame index. `annotation_history.py` stores object references plus only changed locations and fields; never restore a deep-copied panel box list. ImagePanel gestures and label edits notify the frame owner before and after mutation. Confirmations and rejections can affect boxes on other frames, so their history entry must include those changes. Restoring an entry must refresh both image and tag panels while preserving unrelated box identities and metadata.
- Multi-selection belongs to `ImagePanel` and is UI state, not serialized annotation data. Bulk confirm, remove, and not-a-pin actions must update the current frame's actual box list in one owner transaction and one undo entry; feedback is synchronized for every directly changed box. Preserve the earlier rule that only automatic boxes can receive a not-a-pin negative review. Keep selected boxes highlighted until removed or hidden, and prune the selection on frame changes.
- Keep raw media, extracted frames, and generated labels out of commits unless a small fixture is intentionally added. The local `images/` and `labels/` directories contain ignored data; do not modify or clear them as part of routine work.
- For future artwork imports, record source, identifier, rights/usage status, and provenance. A public image URL alone does not establish a reusable training asset.

## Testing and verification

- Use the project `.venv` when present. At the initial scan (2026-10-02), it has Python 3.13, wxPython, OpenCV, NumPy, PyYAML, and pytest. `requirements.txt` lists runtime dependencies but does not currently list pytest.
- Current verification command: `.\.venv\Scripts\python.exe -m pytest -q`. Detection tests live in `tests/test_pin_detection.py`; the existing GUI tag removal test is repaired, and `pytest.ini` registers the `gui` marker.
- Add focused tests as code changes are made. Prefer synthetic NumPy frames, in-memory JSON streams, and temporary files for data, geometry, tracking, and persistence tests. Use wx integration tests for event wiring and visible interaction behavior; give each test its own clean GUI state and destroy windows.
- For a bug fix, add a regression test that fails for the observed behavior before changing it when practical. For a new feature, cover the data path and at least one representative integration path. Avoid tests that only restate implementation details or require the ignored local media.
- Verify affected tests and report the exact command and outcome. GUI smoke checks should state whether they were actually run; a passing unit test does not establish GUI behavior.

## Known prototype boundaries

- Detection is a two-stage OpenCV heuristic followed by a conservative nearest-neighbour feedback ranker, not a trained neural pin detector. Real backing-card artwork can create false proposals and hide real pins. `Detect Pins` adds review candidates; adjacent-frame association and local template search copy tags only for strong matches. Play submits one frame at a time to the worker. The label list refreshes on pause. Explicit GUI detection and Next buttons use the worker; direct `on_next` calls retain the synchronous path for existing integrations. Console logs time decode, detection, tracking, catalog, bitmap, labels, and reconciliation. There is no recovery after long occlusions or scene cuts.
- `ScrubberFrame.find_object_in_next_frame` is legacy ORB code and is not used by the new navigation path. `OpenCVBoxTrainer` remains disconnected and incomplete; this project has no working training pipeline.
- `pin_catalog.py` stores reference images with provenance in SQLite. `pinpanion_sync.py` imports unseen IDs and their images from the public Pinpanion `pins.json` feed at startup in a background thread. The current ORB/FLANN feature index is rebuilt after import and only assigns a `pin_id` for strong geometric matches; accuracy on real pins has not been measured. Source rights are recorded as unverified.
- Saved-frame catalog scans run on the existing worker after adjacent-frame reconciliation, so a tracked identity gets priority and the UI can continue painting. A result commits only if the box and catalog index are still current. The displayed percentage is ORB geometric inlier consistency for a provisional match, not a calibrated probability.
- `mobile_web/` is an Android-accessible web app, not a native APK. It proposes and tracks candidate areas on-device, stores collection records in browser local storage, and caches the public Pinpanion catalog metadata in IndexedDB after an online fetch. Its service worker caches the app shell for offline launches. It does not automatically identify specific pins; the Python ORB matcher has not been ported to the browser. There is no authenticated Pinpanion collection synchronization, neural recognition model, or documented training dataset format yet. Do not guess Pinpanion write endpoints or credentials from the public catalog feed.

## Working style for future agents

- Keep user-facing plans tied to observable milestones: annotation reliability and portability, dataset export and provenance, model evaluation, then mobile/collection integration as separately chosen work.
- State assumptions, unresolved product decisions, tests run, and remaining risks in the handoff. Update this guide when the architecture or commands materially change.
- Add a reusable skill only after a repeatable project workflow exists (for example, annotation-fixture generation or model evaluation) and its steps can be verified. Keep the skill narrower than this repository-wide guide.
