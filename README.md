# Pinident

Pinident is an early annotation and scanning tool for Pinny Arcade pins. The Windows editor reviews video annotations with a Python detector and catalog matcher. The TypeScript mobile web app proposes pin areas from camera frames, photos, and recorded videos directly on the device. The desktop can train an OpenCV pin/non-pin classifier from reviewed crops; there is no trained neural object detector yet.

For current behavior and data contracts, see the [project specification](docs/PROJECT_SPEC.md). The [implementation guide](docs/IMPLEMENTATION_GUIDE.md) maps modules, storage, threading, and verification. Agent-specific invariants are in [AGENTS.md](AGENTS.md), [controls/AGENTS.md](controls/AGENTS.md), and [mobile_web/AGENTS.md](mobile_web/AGENTS.md).

## Run

With Python and the dependencies in `requirements.txt` installed:

```powershell
python displayvideo.py
```

Choose a video or still image in the file dialog. The app loads annotations from `<media-stem>.json` if that file exists and saves them there when the window closes. A still image is treated as a one-frame source, so its reviewed crops can join the same training database as video reviews. **File → Save** writes the current boxes and frame-presence assertions to that JSON file immediately without closing the editor. **File → Load Annotations...** loads a JSON file for the currently open source. Reviewed-crop feedback and catalog SQLite changes are committed as they occur.

Closing the desktop editor opens a progress window. It lists stopping playback/prefetch, finishing active background work (including a requested training run), writing the annotation JSON, and releasing readers. Each row shows a percentage and approximate time remaining, with an overall percentage and estimate. Estimates revise while work runs; a worker without measurable internal progress stays at its current percentage until it finishes. The editor closes only after the annotation file is replaced. If saving fails, the editor stays open and reports the error so you can save again.

**File → Settings** shows the active paths for the reviewed-crop feedback database, known-pin catalog, video annotation JSON, and OpenCV classifier and its metadata, along with each file's last modification status. The paths are selectable for copying. It shows saved review counts, the current in-memory feedback ranker revision, and whether the saved classifier is loaded and current with the stored reviews. It also offers **Detection resolution during Play and Detect Pins**: Regular uses source resolution; Low scales the longest side to 640 pixels for detection and tracking, then maps boxes back to source coordinates. The choice persists for this Windows user and Regular is the default. Low runs faster but can miss or move candidates, so review its boxes. The classifier is saved beside its feedback database as `<database-stem>.svm.yml` with a `.json` metadata file.

**Confirm all suggestions** below the button bar verifies every visible catalog-suggested pin identity on the current frame in one undoable action. It turns those areas into directly confirmed pins and stores one positive review crop per area. Blue candidates, unidentified boxes, manually typed names without a catalog ID, and rejected areas are left alone.

## Detect and tag

Desktop detection does not add a candidate that covers more than half of a smaller existing area. A small edge overlap is allowed. When tracking or identity matching establishes that two mostly overlapping boxes represent the same pin, the editor keeps one box on each saved frame and removes the duplicate crop. Direct reviews, manually entered names, and conflicting confirmed identities are protected when a match is uncertain.

The desktop keeps recently decoded video frames in a shared 128 MiB memory cache and preloads up to four frames ahead while you scrub. Older frames are evicted automatically. This reduces repeated decoding; pin detection and catalog matching still take processing time. Console timing lines separate decode, detection, tracking, catalog matching, and fallback costs.

For a slow frame, compare its `frame=N ui submit=` line with `frame=N worker decode=...` and the later `worker_total=` line. `worker_total` is the complete background analysis time; it is not the time spent queueing the job. The worker line splits `fallback_detect` and `fallback_catalog` as well. Catalog lookups use a bounded descriptor shortlist for large catalogs and still verify a specific pin geometrically.

- **Detect Pins** searches the current frame. It first proposes contrasting regions at a reduced resolution, then tries to tighten each candidate inside its local crop. When refinement is uncertain, it keeps the coarse box for review. It retains existing manual boxes. Unidentified, unconfirmed candidates are **blue**; unconfirmed candidates with a suggested identity are **red**. A pin confirmed to be present but without a verified identity is **orange**, as are linked detections in other frames. A directly presence-confirmed box with a verified identity is **green**. After **Not this pin**, the rectangle stays orange if its pin presence was already confirmed; confirming a new specific identity turns it green again. Its pin-presence review remains saved.
- New automatic candidates are compared with the median width and height of directly presence-confirmed, fully visible pins in the same frame; their specific identity need not be known. If none are visible, inherited observations from confirmed pin tracks supply the size reference. Without either reviewed source, a clear majority of at least three similarly sized visible boxes can supply the reference. Each full dimension must be about 50%–150% of that reference. Even if the larger boxes vary in size, three distinct boxes more than twice as wide and high can rule out a tiny new candidate. The same check removes only a provisional pin name from an older unconfirmed automatic box; its area remains available for review. This applies to normal and fallback detection. Direct reviews and boxes tracked from another frame are kept; a pin partly clipped by the frame edge may be narrower along that edge. Physical pin sizes cannot be converted to image pixels without a scale reference.
- Tag a candidate in the panel beside the image. Manual **Next** and **Previous** steps run the same primary detector and empty-frame fallback as **Detect Pins** on unprocessed frames, then match proposals to the frame just left. They copy tags only when the appearance and position agree. A local template search can preserve a tagged pin when the general proposal stage misses it.
- When you move to a Previous or Next frame, the editor uses identified or confirmed boxes in the frame you just left, even if the destination was processed before. It links visually matching saved candidates, including blank manually drawn boxes, while preserving a different name entered by the user. If a strong local image match finds the reviewed area inside an overlapping unreviewed automatic candidate, the editor keeps the tracked area and removes the duplicate candidate. It can follow a contiguous chain in either direction, assign the same durable track ID, and copy an established pin identity into matching candidates. These linked boxes become orange when the chain contains a user confirmation; an identity without confirmation remains unconfirmed. A user-confirmed identity can correct a conflicting provisional catalog match. During Play, each newly processed frame is linked to the adjacent frame in the worker. Manual navigation runs its checks on the worker, then updates the boxes on the UI thread if the annotations have not changed.
- A pin entering from any frame edge can start as a narrow visible fragment. The next frame may use a larger box when more of it comes into view. Tracking compares the fragment with the matching part of a larger detector or saved box, and local search can grow a near-edge box when detection misses. The original frame keeps its clipped coordinates; each later box stays within its own frame. This still requires a strong visual match, so review edge objects that change appearance or pass close to other pins.
- A confirmed catalog identity remains authoritative through orange linked frames. When a tracked detection matches a saved candidate with a conflicting unconfirmed catalog guess, the confirmed identity replaces that guess. If appearance tracking misses a new detection because its view changed, a strong catalog match to the same identity plus substantial overlap with the adjacent confirmed box can still link it and show the inherited orange state. Confirming only that an object is a pin tracks its presence without approving its suggested name. Linked boxes with verified identities skip another lookup; confirmed or inherited boxes without a verified identity are scanned before ordinary candidates on frame changes and Detect Pins. The scan checks the known-pin catalog and reviewed positive/negative-identity crops. Unconfirmed suggestions show a percentage before the pin name; it is a match-strength score, not a calibrated probability. A question mark marks a suggested identity on a pin whose presence was confirmed. The score is saved with the suggestion and carried along unconfirmed tracks. Editing the name clears the old catalog ID and score.
- The catalog can recheck an automatic box whose name is only a provisional guess, and can suggest an identity for a directly presence-confirmed but unnamed pin, including a manually drawn box. It prefers a geometrically verified stock-image match. If geometry is inconclusive, a name appears only when stock-image colour and image layout agree strongly and one pin clearly leads the others. Otherwise the area stays unidentified; a later scan can clear an older unverified guess. The displayed percentage is visual match strength, not the chance that the name is correct. Saved-frame rechecks run in the background after adjacent-frame tracking, while verified identities, rejections, and manually entered names remain protected.
- When a verified identity visually matches an adjacent presence-only confirmed box, that frame inherits the verified identity while keeping its own pin-presence confirmation. The saved `identity_inferred` flag distinguishes this tracked identity from a direct user confirmation, so correcting the original confirmation withdraws the inferred identity. The right-pane tag field is an editable Pinpanion catalog picker. After a short pause in typing, it searches the full catalog for names or IDs containing the complete query, ignoring letter case. The results popup shows the first 75 matches, so keep typing to narrow a broad search. The dropdown returns focus to the name field, and refreshed catalog choices preserve text being typed; click a result to select it. Unique names are shown without an ID; duplicate names show their IDs. Choosing an option saves its stable pin ID, while typing a custom name remains possible.
- Hover over a box edge or corner to see its resize cursor, then drag to adjust the boundary. Drag inside a box to move it. These edits update the same source-image coordinates shown in the tag panel and saved in JSON, including when the image is scaled or rotated.
- When you correct an automatically detected rectangle, adjacent-frame tracking carries that crop adjustment forward and scales it as the object changes size. Play can tighten an overlarge automatic box or grow a narrow one as a pin enters from any edge when the image match is strong. Revising or undoing the correction updates linked rectangles that have not been edited separately. A later frame with its own edited or reviewed rectangle keeps its own bounds. The tracked correction stays in the annotation JSON so later training indexing uses the corrected crop.
- **Ctrl-click** boxes to add or remove them from a selection. Drag a rectangle from empty image space to select any visible box whose area is more than half covered by the drag; if none qualify, the drag creates a new manual box. Selected boxes have thicker borders. Right-click any selected box (or empty image space while the group remains selected) to **Confirm selected identities** for the labels currently shown, **Confirm selected as pins** when the group includes an unnamed box, **Not a pin (automatic only)**, or **Remove selected areas**. Mixed groups can confirm their named identities without confirming unnamed boxes, and pending label edits are saved before the action. A bulk action is one undo step. The not-a-pin action leaves manually drawn boxes untouched and retains negative training crops for the selected automatic boxes.
- With no text field active, press **Del** to remove selected boxes without pin/non-pin feedback, **N** to mark selected automatic boxes as **Not a pin**, or **X** to mark a single selected named box as **Not this pin** and request another catalog suggestion. The menus underline letter shortcuts and show Del on removal items. Ctrl+X retains its normal text-editing behavior.
- The tick beside a box's labels confirms **is a pin**; the bin uses **Remove area**. The image box's right-click menu offers **Confirm is a pin** for an unidentified area and **Confirm pin identity** for a named pin, plus **Remove area**. Select a named rectangle and press **Y** to confirm its identity; the shortcut leaves the name text field free for typing. Named boxes also offer **Not this pin**; automatically added areas offer **Not a pin**. Identity confirmation is available only when a specific catalog ID or non-placeholder name is present. A newly drawn box starts as a confirmed pin-presence observation with a blank editable name in the right pane, not an `unknown-#` name. It immediately checks that rectangle against the known-pin catalog and reviewed identity crops; any result is an unconfirmed identity suggestion. **Remove area** deletes only that frame's annotation without teaching the model anything. **Not a pin** saves a hidden negative review and follows the same visually matching object through contiguous saved frames in either direction, hiding those automatic detections. A distinct object in that area can still be proposed, and you can draw a new box to correct a mistaken rejection.
- **Replace with pin** in a box's right-click menu lists up to 10 catalog matches for that rectangle with match scores. The current suggested ID appears in the first page even when its geometric or reviewed-crop match falls outside the colour-and-layout-ranked top ten. When available, each label shows the pin's year and show between the score and name, for example `99% [2021/West] Some pin`; entries with only a year show `[2021]`. Choosing one directly confirms that pin identity and, when replacing a different named suggestion, records the old identity as incorrect. **none of these** at the bottom records each listed ID as an incorrect match for that rectangle, retries identity detection on that rectangle while excluding those IDs, and opens the next ranked set. The list ranks by stock-image colour and layout for manual selection; its percentages are similarity scores rather than calibrated probabilities or proof of identity.
- **Attempt detection** in a rectangle's right-click menu scans that rectangle again against the known-pin catalog and reviewed identity crops. A strong reviewed-crop identity can replace a weak catalog appearance match; a geometrically verified catalog match keeps priority. A credible identity is attached as an unconfirmed suggestion to the same rectangle. If both checks abstain, an old unverified suggestion is cleared. A direct identity confirmation or manually entered name stays unchanged. The scan runs on the worker and is discarded if the box changes or you navigate away before it finishes.
- **Ctrl+Z** undoes the latest edit on the current frame; **Ctrl+Shift+Z** redoes it. Draw, move, resize, tag, confirm, remove, reject, and rotation actions keep the original box objects and only restore fields changed by that action. A tracked rejection or confirmation can also restore the boxes it affected in adjacent frames. Undo history lasts for the current editor session; the resulting annotations are saved in the normal JSON sidecar.
- **Play** processes the current frame and then advances through the remaining frames, detecting and tracking on a background worker. The next frame is scheduled only after the current result is displayed, leaving the UI event loop free for Pause and clicks. **Next** and **Previous** change the selected frame immediately. On an unprocessed frame, a manual step runs detection on the worker using the frame just left as a tracking reference. Play runs a bounded relaxed search near frame edges when adjacent frames change meaningfully, so newly entering pins can get review boxes even beside an existing tracked pin. Static frames skip that search; manually revisiting an empty Play-processed frame runs the full search once. Later navigation cancels stale results so an old worker job cannot move the view back. **Detect Pins** also runs on the worker. Click the image or a candidate to pause, make corrections, then press Play to resume. Pending results are discarded when playback pauses. The label list updates when playback stops so it does not rebuild for every frame.
- The frame-number scale above the bottom slider shows fewer interval labels when the window is narrow or the video has many frames. Resize the window to see more marks; the first and last frame remain labeled when space permits.
- **Contains pin** means at least one pin is known or the user has asserted one is present. **Contains set** means at least two. Identifying or confirming boxes checks these automatically. Checking either box while too few pins are marked starts detection on the background worker, including an extra contrast-normalized search when the normal detector misses. **Detect Pins** and manual navigation to an unprocessed frame also run that extra search if the normal pass finds no candidates. Extra blue candidates still need review; the checked assertion remains visible if nothing is found. Removing the last marked pin clears both checkboxes, and removing one of two clears **Contains set**. The assertions are saved in `_frame_presence` in the annotation JSON; older files remain readable.

The desktop console prints millisecond timings per frame for decode, detection, tracking, catalog matching, UI commit, reconciliation, bitmap preparation, and label updates. Decoder logs include `thread=ui` or `thread=worker` and `mode=cache`, `sequential`, or `seek`. Repeated and adjacent reads reuse the current frame or advance the capture instead of seeking. Use these timings with a representative video to find the remaining bottleneck; codec decoding and detection speed depend on frame size, candidate count, and catalog size. The image panel already paints through a wx back buffer.

To investigate misplaced or excessive rectangles, press **Detect Pins** once and copy the console lines beginning `PINIDENT_DETECTION` through `PINIDENT_DETECTION end`. The shared `run` value groups the worker and display records. `primary_xywh` and `relaxed_xywh` are detector proposals in unrotated source-image pixels after crop filtering; each final `box` line gives its source rectangle, displayed panel rectangle, existing/new origin, review state, suggested tags/ID, and match strength. `display` records frame and panel sizes, rotation, and the bitmap offset. If source rectangles already point at background, inspect proposal and filtering behavior; if source rectangles point at pins but panel rectangles are misplaced, inspect the display transform. A blank `pin_id` means the rectangle was proposed as a possible pin, with no specific identity found. These logs do not include image pixels, so include a screenshot or describe where the actual pins are when reporting a problem.

For the mobile web scanner, pause a video or load a photo and copy the browser console's `PINIDENT_DETECTION web` JSON line. A live scan with 15 or more visible areas also logs at most once every 10 seconds. The line contains original source dimensions, bounded scan dimensions, proposal rectangles, model-rejected, below-match-threshold, and size-filtered rectangles, final scan rectangles, provisional catalog IDs and match strengths, and their overlay positions in stage CSS pixels. `pin_id` and `name` remain empty until a user tags a track; `suggested_pin_id` is provisional. Include a screenshot with the log when reporting misplaced boxes.
- Each new box has a `track_id`, `review_state`, and `identity_confirmed` in the JSON sidecar. A matched box retains its track ID across frames. Direct pin-presence confirmation is saved as `confirmed`; linked boxes become `inherited`. `identity_confirmed` separately records whether the displayed specific name was approved. Rejected automatic candidates are saved as hidden `rejected` observations so future detection can use that decision. Catalog matches also save a `pin_id` and optional `match_confidence`. Editing a box's tags clears its catalog ID, score, and identity confirmation so a correction cannot retain an outdated match. Older JSON files still load; a legacy confirmed box with a specific name is treated as identity-confirmed, while old cross-frame links cannot be reconstructed automatically.

## Known pin catalog

Reference images are stored in the local `known_pins.sqlite3` database. On startup, the app checks [Pinpanion's public `pins.json` feed](https://pinpanion.com/pins.json) in a background thread. It imports only IDs not already in the database, along with each pin's name, full feed metadata, and image from Pinpanion's `/imgs/` path. It also stores event names for the year/show labels and refreshes the match list when those names change. Pinpanion IDs are stored as `pinpanion:<id>` to avoid collisions with local IDs. Failed images are retried at the next startup. The window remains usable offline and while a first import is running; existing candidates are rechecked when the updated index is ready. The database is local and ignored by Git.

The app records the image URL and marks the source's rights status as **unverified**. Confirm permission for reuse and model training before distributing the images or a model trained from them.

You can also add local images with a stable pin ID, name, source, and rights status:

```powershell
python pin_catalog.py pa-001 "Example Pin" C:\path\to\reference.png --source "My collection photo" --rights "Personal use"
```

Run the command again with the same ID and name to add more views of one pin. Restart the viewer after adding references. The matcher builds an approximate feature index from catalog images and checks geometric agreement for its best candidates. Weak or ambiguous matches stay as Candidates. This is an initial recognition baseline, not a trained deep learning model: artwork-only references may differ substantially from photographed pins, and accuracy needs evaluation on real annotated frames.

The detector is deliberately conservative about copying tags, but its candidate proposals are still heuristic. Printed card artwork, fingers, and background texture can produce false candidates; low-contrast or partly occluded pins can be missed. Review all proposed identities and correct the boxes before using annotations as training data. Re-identification after a long disappearance and bulk training-data export are future work.

### Detection feedback

Confirming a box records a **positive** pin example. Choosing **Not a pin** on an automatic area records a **negative** non-pin example and withdraws an earlier positive review on the same automatic track. The rejected box remains in the annotation JSON with its coordinates, track ID, and original detector suggestion, but is hidden from the image and label list. The negative training example contains the image crop and a non-pin label; a rejected catalog suggestion is retained only as annotation provenance, not as a true pin ID for that example. Examples are saved in the ignored local `detection_feedback.sqlite3` database as PNG crops with source video path, frame number, track ID, box coordinates, and an unverified rights status. The annotation JSON marks only direct user decisions as feedback. During **Add to training data**, every saved orange frame view linked to a directly confirmed pin adds its own positive crop, without becoming another direct review. Propagated rejections still add no duplicate negative. Existing confirmed boxes and one representative per legacy rejected track are imported when annotations load; unchanged linked crops already indexed are retained. Undo and redo update direct examples, while the next training indexing pass reconciles linked crops after edits. **Remove area** never teaches the detector that the area contains no pin; deleting a confirmed annotation removes its associated positive example.

**Not this pin** keeps the box and any pin-presence confirmation. It records the rejected ID/name, rectangle, frame, and image crop in a separate wrong-identity table, clears that name from matching boxes on the same track, and retries the selected rectangle against the catalog and reviewed identity crops while excluding that rejected identity. The next suggestion appears on the rectangle, or the status bar reports that no other match was found. The review is saved in the annotation JSON and restored on load; undo and redo update its stored crop. It does not create a non-pin example. The local identity matcher also uses the saved wrong-ID crop to block visually similar incorrect suggestions for that pin ID. It remains a nearest-neighbour baseline, not a trained neural classifier.

Desktop detections pass coarse proposals through a small nearest-neighbour feedback ranker built from pin/non-pin reviewed crops. It promotes proposals similar to confirmed pins and suppresses close matches to rejected candidates when no comparable positive example exists. The same local model can suggest a pin ID from directly verified positive crops when its visual similarity is strong and clearly ahead of other IDs. A visually similar wrong-ID review vetoes that ID. These vectors refresh after affected reviews, undo, redo, or annotation import. Stored crop descriptors load in the background at startup; the status bar reports progress while the review ranker becomes ready. A separately trained OpenCV SVM, when available, classifies proposed rectangles as pin or non-pin and downranks predicted non-pins. It does not discard a rectangle on its prediction alone, since clean stock artwork can differ sharply from pins in video frames. A saved classifier is loaded on the next launch even if newer reviews or catalog images make it stale; Settings reports that state, and **Run training now** updates it. **Training → Feedback model...** explains both paths and shows saved and usable review counts. A crop with too little visual detail remains saved but cannot affect either model. Console logs report each revision and, for each detection pass, how many proposals the trained classifier ranked as negative.

**Add to training data** saves the current session annotations, compares direct pin/non-pin and wrong-identity reviews plus saved inherited pin views with the local feedback database, and extracts crops only for new or modified observations. Each saved frame on a confirmed pin track gets a distinct positive crop and stable example ID, so changes in viewing angle, blur, rotation, and apparent size can contribute separately. Unvisited frames are not automatically scanned by this command, and unconfirmed proposals are not assumed to be pins. It refreshes the in-memory nearest-neighbour ranker immediately; it does not fit the saved OpenCV classifier. **Run training now** first performs that same indexing step, then fits or continues the linear pin/non-pin classifier using stored reviewed crops from every media source and usable Pinpanion stock images. It needs at least one usable pin image or reviewed pin crop and one usable reviewed non-pin crop. The trained model is saved to `<database-stem>.svm.yml` and used to classify future detector proposals; its metadata file records the feature version, reviewed and stock counts, training-data fingerprint, and stock-image provenance. This is a rectangle classifier, not a full-image neural object detector: the coarse proposal stage must still find an area before it can be classified. No accuracy claim is made without a held-out evaluation. **None of these** creates one wrong-identity review for each distinct pin in the displayed menu page; a full page creates 10 separate records for the same rectangle and 10 different pin IDs. Those crops are saved immediately in the feedback database's separate `identity_rejections` table. The right pane reports how many rows that menu action actually saved; a final page may contain fewer than 10 pins. For example, 60 pages of 10 distinct rejected pins produce 600 wrong-identity records. Because these rows are already stored, a later **Add to training data** run may report zero newly added rows while showing the full wrong-ID total. Deleted reviews are removed from the database without decoding frames. An unchanged session finishes immediately, without rebuilding the in-memory ranker. Progress and ETA reflect only crops that still need processing; the final status separates linked pin views, other pin crops, non-pin crops, wrong-ID reviews, and added, updated, and removed counts. Confirmed pin IDs and trusted linked views become identity exemplars in the local nearest-neighbour model; wrong-ID reviews exclude those IDs on the tracked object and veto similar model suggestions. Propagated copies of one rejection are not counted as independent examples.

Newly drawn manual rectangles count as positive pin crops even when their pin ID is unknown. They are saved when drawn, so **Add to training data** can report zero added now while still showing them in its indexed pin-crop total and its count without verified IDs. **Run training now** includes usable unnamed pin crops and every usable locally stored Pinpanion stock image when fitting the pin/non-pin classifier. It reads the stock images directly from `known_pins.sqlite3` and retains their pin IDs, names, image URLs, and rights status in the model metadata; stock images do not become review rows in `detection_feedback.sqlite3`. It reports usable versus total stock images and needs at least one reviewed non-pin crop. The completion status separates reviewed pin crops, stock pin images, and non-pin crops. This remains a pin/non-pin rectangle classifier; specific pin suggestions still come from catalog and reviewed-identity matching.

The ranker cannot recover an object that the proposal stage never finds. **Detect Pins** and manual navigation to an unprocessed frame try a contrast-normalized fallback when the primary pass yields no candidates. Playback also tries a bounded edge search when adjacent frames change; the status bar reports primary and fallback counts or that no candidates were found. The fallback rejects many small repeating background textures but can still find backing-card artwork, so review the blue boxes. Negative feedback now suppresses moderately similar rejected crops as well as near-identical ones, while a stronger positive match protects a proposal. These changes have synthetic regression tests but have not been measured on representative collection footage. Desktop crops remain local; reviewed web crops are uploaded to the shared dataset. Confirm source reuse rights before publishing a model.

After the first fit, **Run training now** continues the saved linear classifier when the training set has only gained examples. It updates the existing decision weights with new crops and rehearses retained crops from earlier videos and images. An unchanged run leaves the weights alone. Correcting or removing a review triggers a fresh fit from the current full crop set, so the superseded review does not keep influencing the model. The saved model and its metadata are both needed to continue training; keep them together with `detection_feedback.sqlite3` when moving to another computer. Updating or removing a review reconciles only that media source. Specific pin identities remain in annotation JSON and reviewed identity crops, since the classifier learns only pin versus non-pin.

When training finishes successfully, the desktop immediately installs the updated classifier for new Detect Pins, navigation, and Play jobs in the same open session. A queued detection based on the previous model is discarded. A later cloud refresh does not replace a current local trained classifier.

## Mobile scanner

The photo preview follows the loaded image's aspect ratio and contains the entire image within the stage, including portrait camera photos. Boxes and touch drags use the same fitted image coordinates, so pins near the bottom can be selected or drawn without cropping. The preview may show side margins when its height is capped on a phone.

While the camera or a recorded video scans, **Pause to annotate frame** and **OK — Save and finish** replace the four source choices at the top. Pause keeps the current frame available for tagging, drawing, training review, or saving; Resume video returns to scanning. The source choices return after the scan is finished or stopped.

Tap **OK — Save and finish** after tagging to save the current scanned frame and its areas, stop the camera or video, and return Scan to its ready state. The frame is saved on this device before the scan closes; Cloudflare upload is queued and can complete later when online. If local saving fails, the frame stays open for another attempt. **Stop without saving** ends the scan and discards changes made since the last save.

On a paused photo or video frame, **Select or draw** is the default drag tool. A drag selects each existing rectangle it covers by more than 50%; if it covers none, it draws a new area. **Draw area** always adds a rectangle, including over an existing one, while **Select areas** always selects. The gold outline shows selection; deletion still requires **Delete area(s)**.

The on-device detector now considers close-up silhouettes spanning most of the frame and suppresses smaller detail rectangles inside a larger proposal. It still proposes isolated small objects. This was checked with synthetic frames; real phone camera performance has not been measured.

The mobile app is a TypeScript progressive web app (PWA) built for Cloudflare Workers Static Assets. Install Node.js 24 or newer, then from `mobile_web/` run:

```powershell
cd mobile_web
npm ci
npm run typecheck
npm test
npm run dev
```

Automatic web identity suggestions use a compact reference index built from the local catalog images. From the repository root, generate an ignored **local-only** index and preview it with:

```powershell
.\.venv\Scripts\python.exe build_identity_index.py
cd mobile_web
npm run dev:local-index
```

New automatic boxes wait for a provisional catalog visual match of at least 50% match strength. The highest-scoring area supplies the size reference; fresh untracked boxes must be roughly 50%–150% of its width and height, with a clipped-edge exception. A stronger match found later replaces that reference. The overlay and result card show the suggested pin name and match percentage. This percentage is a relative visual score, not a measured probability; verify each identity before saving it as a known pin. Manually drawn areas and previously tagged tracks remain usable when no reference index is available. Directly tagged pin crops add local reference examples, and rejected/not-pin crops add local veto examples on that browser.

The current 1,814 stored Pinpanion artwork records say `source terms unverified`. The local index is ignored by Git, and the deploy commands refuse to package an index until its rights are verified. After obtaining rights clearance and recording it in the catalog, `build_identity_index.py --publish` writes the publishable asset. The new matcher and gate are not deployed on the development or production site yet.

In **Scan**, use the live camera, take a photo, choose a gallery image, or open a recorded video. Tap **Pause to annotate frame** during a camera or video scan to review its current frame, then Resume video or save the annotation. Drag on the preview to add a missing area, tag it from the catalog or mark it as a pin with unknown identity, and choose **Save frame annotation**. Saved frames include their bounded image, all boxes, source filename, and video time when available. **Review areas for training** queues candidate crops from that still frame. Training mode asks whether each crop is not a pin, a pin with unknown identity, the suggested pin when an actual suggestion exists, or another catalog pin selected through search and a dropdown. **Unknown**, beside **This is not a pin**, means the crop is too difficult to judge. It does not label the crop as pin or non-pin and does not change its scan annotation; similar crops appear after clearer candidates in future review queues. The mark and image stay in local IndexedDB, while only a compact visual signature syncs to Cloudflare for shared ordering. Each definite training review uploads its crop and label to Cloudflare D1. Saved frame annotations upload the bounded frame image and boxes to the same D1 event log; the desktop uses each confirmed pin box as a separate positive crop. Offline uploads retry on reconnect. Collections remain local. The review and annotation rights status is unverified. Wait for cloud sync to finish before clearing browser site data.

To remove unwanted rectangles while annotating a paused image, tap a rectangle or use **Select** on its card, then press **Delete area**. You can select several by tapping them individually. npx wrangler d1 migrations apply pinident-training-dev --env dev --remote
```powershell
npm run deploy:dev
```

The development secret survives ordinary redeployments. For a fresh environment or rotation, use `npx wrangler secret put SYNC_TOKEN --env dev`, then set the same long random value in the desktop process as `PINIDENT_SYNC_TOKEN`; set `PINIDENT_SYNC_URL=https://id.dev.pinpanion.com`. Never put the token in browser files, `wrangler.jsonc`, or source control. For production, create `pinident-training-prod`, add its database ID to the top-level binding, apply its migration, deploy with `npm run deploy:prod`, and set a **different** production secret. Leave `PINIDENT_SYNC_URL` unset to select production. Verify HTTPS, review upload/pull, and authorized model upload before relying on either environment. The Worker accepts public same-origin review submissions, so configure Cloudflare rate limiting and monitor submissions before inviting general traffic. Cloudflare creates custom-domain DNS records and TLS certificates when attachment succeeds.

`pinident.pages.dev` is a Cloudflare **Pages** project hostname and is not created by this Workers deployment. The requested `id.dev.pinpanion.com` development hostname is configured directly. A separate Pages deployment would be needed if that optional alias becomes useful. The optional Python preview on port 8765 serves the same catalog route after `npm run build`.

The Worker serves `/catalog.json` from the same [Pinpanion `pins.json` file](https://pinpanion.com/pins.json) used by the Windows catalog importer; it does not scan images. Production and dev are distinct browser origins, so their on-device collections and cached catalog data are separate. Export a collection if it needs to move between them.

On Android, first open the deployed HTTPS URL while connected, then use the browser's **Install app** or **Add to Home screen** action. The service worker caches the app shell. After that first successful load, the app can be opened and used for candidate detection, local tags, collections, and export without an internet connection. The first successful online fetch stores a parsed copy of the Pinpanion feed's pin IDs, names, and filter metadata in IndexedDB for offline browsing and selection. This cache is not a separate hand-maintained list of valid pins. If no catalog was cached, a local unknown-pin name still works offline and stays outside the known-pin catalog. Reference artwork is not bundled or guaranteed offline. Clearing browser site data can remove the cache and local library, so export important collections.

**Automatic identification of a specific pin is not yet available offline.** The downloaded classifier predicts only pin versus non-pin for proposed areas; users still choose a valid identity from the filtered, cached catalog. A separate local placeholder is available for pins missing from the catalog. The desktop Python ORB matcher cannot run in this static app; offline automatic identity needs an evaluated browser-compatible model and distributable reference assets. Candidate detection and the classifier have not been evaluated on representative phone footage.

Pinpanion **collection write access is not connected yet**. The public `pins.json` feed supplies pin metadata and images, but does not document user login, collection IDs, or a supported write endpoint. Saved collections stay in that browser's local storage until an authorized Pinpanion integration is available. Local custom pin IDs (`local:<id>`) are distinct from Pinpanion IDs (`pinpanion:<id>`), so a future sync can distinguish them. Do not clear browser site data without exporting the library first.
