# Pinident

Pinident is an early annotation and scanning tool for Pinny Arcade pins. The Windows editor reviews video annotations with a Python detector and catalog matcher. The TypeScript mobile web app proposes pin areas from camera frames, photos, and recorded videos directly on the device. There is no trained neural classifier yet.

## Run

With Python and the dependencies in `requirements.txt` installed:

```powershell
python displayvideo.py
```

Choose a video in the file dialog. The app loads annotations from `<video-stem>.json` if that file exists and saves them there when the window closes. `Load Annotations...` loads a JSON file for the currently open video.

## Detect and tag

- **Detect Pins** searches the current frame. It first proposes contrasting regions at a reduced resolution, then tries to tighten each candidate inside its local crop. When refinement is uncertain, it keeps the coarse box for review. It retains existing manual boxes. Unidentified candidates are **blue**; identified detections awaiting review are **red**. A user-confirmed pin is **green**, and linked detections in other frames are **orange** until confirmed directly.
- Tag a candidate in the panel beside the image. Manual **Next** and **Previous** steps run the same primary detector and empty-frame fallback as **Detect Pins** on unprocessed frames, then match proposals to the frame just left. They copy tags only when the appearance and position agree. A local template search can preserve a tagged pin when the general proposal stage misses it.
- When you move to a Previous or Next frame, the editor uses identified or confirmed boxes in the frame you just left, even if the destination was processed before. It links visually matching saved candidates, including blank manually drawn boxes, while preserving a different name entered by the user. If no box exists near an identified pin, a strong local image match can add a tracked box to the destination without running the full detector again. It can follow a contiguous chain in either direction, assign the same durable track ID, and copy an established pin identity into matching candidates. These linked boxes become orange when the chain contains a user confirmation; an identity without confirmation remains unconfirmed. A user-confirmed identity can correct a conflicting provisional catalog match. During Play, each newly processed frame is linked to the adjacent frame in the worker. Manual navigation runs its checks on the worker, then updates the boxes on the UI thread if the annotations have not changed.
- A confirmed catalog identity remains authoritative through orange linked frames. When a tracked detection matches a saved candidate with a conflicting unconfirmed catalog guess, the confirmed identity replaces that guess. If appearance tracking misses a new detection because its view changed, a strong catalog match to the same identity plus substantial overlap with the adjacent confirmed box can still link it and show the inherited orange state. Confirming only that an object is a pin tracks its presence without approving its suggested name. Linked boxes skip another catalog lookup. Unconfirmed catalog suggestions show a percentage before the pin name; this is the share of geometrically consistent ORB feature matches, not a calibrated probability. A question mark marks a suggested identity on a pin whose presence was confirmed. The score is saved with the suggestion and carried along unconfirmed tracks. Editing the name clears the old catalog ID and score.
- The catalog can recheck an automatic box whose name is only a provisional guess, and can suggest an identity for a directly presence-confirmed but unnamed pin, including a manually drawn box. It keeps the strongest distinct reference match and shows its ORB match-strength percentage beside the name. Saved-frame rechecks run in the background after adjacent-frame tracking, while verified identities, inherited track identities, rejections, and manually entered names remain protected.
- When a verified identity visually matches an adjacent presence-only confirmed box, that frame inherits the verified identity while keeping its own pin-presence confirmation. The saved `identity_inferred` flag distinguishes this tracked identity from a direct user confirmation, so correcting the original confirmation withdraws the inferred identity. The right-pane tag field is an editable Pinpanion catalog picker. After a short pause in typing, it searches the full catalog for names or IDs containing the complete query, ignoring letter case. The results popup shows the first 75 matches, so keep typing to narrow a broad search. Unique names are shown without an ID; duplicate names show their IDs. Choosing an option saves its stable pin ID, while typing a custom name remains possible.
- Hover over a box edge or corner to see its resize cursor, then drag to adjust the boundary. Drag inside a box to move it. These edits update the same source-image coordinates shown in the tag panel and saved in JSON, including when the image is scaled or rotated.
- **Ctrl-click** boxes to add or remove them from a selection. Drag a rectangle from empty image space to select any visible box whose area is more than half covered by the drag; if none qualify, the drag creates a new manual box. Selected boxes have thicker borders. Right-click any selected box (or empty image space while the group remains selected) to **Confirm selected as pins**, **Not a pin (automatic only)**, or **Remove selected areas**. A bulk action is one undo step. The not-a-pin action leaves manually drawn boxes untouched and retains negative training crops for the selected automatic boxes.
- With no text field active, press **Del** to remove selected boxes without pin/non-pin feedback, **N** to mark selected automatic boxes as **Not a pin**, or **X** to mark a single selected named box as **Not this pin** and request another catalog suggestion. The menus underline letter shortcuts and show Del on removal items. Ctrl+X retains its normal text-editing behavior.
- The tick beside a box's labels confirms **is a pin**; the bin uses **Remove area**. The image box's right-click menu offers **Confirm is a pin**, **Confirm pin identity**, and **Remove area**. Named boxes also offer **Not this pin**; automatically added areas offer **Not a pin**. Identity confirmation is available only when a specific catalog ID or non-placeholder name is present. A newly drawn box starts with a blank editable name in the right pane, not an `unknown-#` name. **Remove area** deletes only that frame's annotation without teaching the model anything. **Not a pin** saves a hidden negative review and follows the same visually matching object through contiguous saved frames in either direction, hiding those automatic detections. A distinct object in that area can still be proposed, and you can draw a new box to correct a mistaken rejection.
- **Replace with pin** in a box's right-click menu lists up to 20 catalog matches for that rectangle with match scores. Choosing one directly confirms that pin identity and, when replacing a different named suggestion, records the old identity as incorrect. **none of these** at the bottom records each listed ID as an incorrect match for that rectangle and opens the next ranked set; undo restores the previous set. The list ranks by colour appearance for quick interaction, so its percentages are similarity scores rather than calibrated probabilities or proof of identity.
- **Ctrl+Z** undoes the latest edit on the current frame; **Ctrl+Shift+Z** redoes it. Draw, move, resize, tag, confirm, remove, reject, and rotation actions keep the original box objects and only restore fields changed by that action. A tracked rejection or confirmation can also restore the boxes it affected in adjacent frames. Undo history lasts for the current editor session; the resulting annotations are saved in the normal JSON sidecar.
- **Play** processes the current frame and then advances through the remaining frames, detecting and tracking on a background worker. The next frame is scheduled only after the current result is displayed, leaving the UI event loop free for Pause and clicks. **Next** and **Previous** change the selected frame immediately. On an unprocessed frame, a manual step runs detection on the worker using the frame just left as a tracking reference. Play skips the relaxed empty-frame search to avoid flooding the video with speculative boxes; manually revisiting an empty Play-processed frame runs that search once. Later navigation cancels stale results so an old worker job cannot move the view back. **Detect Pins** also runs on the worker. Click the image or a candidate to pause, make corrections, then press Play to resume. Pending results are discarded when playback pauses. The label list updates when playback stops so it does not rebuild for every frame.
- **Contains pin** means at least one pin is known or the user has asserted one is present. **Contains set** means at least two. Identifying or confirming boxes checks these automatically. Checking either box while too few pins are marked starts detection on the background worker, including an extra contrast-normalized search when the normal detector misses. **Detect Pins** and manual navigation to an unprocessed frame also run that extra search if the normal pass finds no candidates. Extra blue candidates still need review; the checked assertion remains visible if nothing is found. Removing the last marked pin clears both checkboxes, and removing one of two clears **Contains set**. The assertions are saved in `_frame_presence` in the annotation JSON; older files remain readable.

The desktop console prints millisecond timings per frame for decode, detection, tracking, catalog matching, UI commit, reconciliation, bitmap preparation, and label updates. Decoder logs include `thread=ui` or `thread=worker` and `mode=cache`, `sequential`, or `seek`. Repeated and adjacent reads reuse the current frame or advance the capture instead of seeking. Use these timings with a representative video to find the remaining bottleneck; codec decoding and detection speed depend on frame size, candidate count, and catalog size. The image panel already paints through a wx back buffer.
- Each new box has a `track_id`, `review_state`, and `identity_confirmed` in the JSON sidecar. A matched box retains its track ID across frames. Direct pin-presence confirmation is saved as `confirmed`; linked boxes become `inherited`. `identity_confirmed` separately records whether the displayed specific name was approved. Rejected automatic candidates are saved as hidden `rejected` observations so future detection can use that decision. Catalog matches also save a `pin_id` and optional `match_confidence`. Editing a box's tags clears its catalog ID, score, and identity confirmation so a correction cannot retain an outdated match. Older JSON files still load; a legacy confirmed box with a specific name is treated as identity-confirmed, while old cross-frame links cannot be reconstructed automatically.

## Known pin catalog

Reference images are stored in the local `known_pins.sqlite3` database. On startup, the app checks [Pinpanion's public `pins.json` feed](https://pinpanion.com/pins.json) in a background thread. It imports only IDs not already in the database, along with each pin's name, full feed metadata, and image from Pinpanion's `/imgs/` path. Pinpanion IDs are stored as `pinpanion:<id>` to avoid collisions with local IDs. Failed images are retried at the next startup. The window remains usable offline and while a first import is running; existing candidates are rechecked when the updated index is ready. The database is local and ignored by Git.

The app records the image URL and marks the source's rights status as **unverified**. Confirm permission for reuse and model training before distributing the images or a model trained from them.

You can also add local images with a stable pin ID, name, source, and rights status:

```powershell
python pin_catalog.py pa-001 "Example Pin" C:\path\to\reference.png --source "My collection photo" --rights "Personal use"
```

Run the command again with the same ID and name to add more views of one pin. Restart the viewer after adding references. The matcher builds an approximate feature index from catalog images and checks geometric agreement for its best candidates. Weak or ambiguous matches stay as Candidates. This is an initial recognition baseline, not a trained deep learning model: artwork-only references may differ substantially from photographed pins, and accuracy needs evaluation on real annotated frames.

The detector is deliberately conservative about copying tags, but its candidate proposals are still heuristic. Printed card artwork, fingers, and background texture can produce false candidates; low-contrast or partly occluded pins can be missed. Review all proposed identities and correct the boxes before using annotations as training data. Re-identification after a long disappearance and bulk training-data export are future work.

### Detection feedback

Confirming a box records a **positive** pin example. Choosing **Not a pin** on an automatic area records a **negative** non-pin example and withdraws an earlier positive review on the same automatic track. The rejected box remains in the annotation JSON with its coordinates, track ID, and original detector suggestion, but is hidden from the image and label list. The negative training example contains the image crop and a non-pin label; a rejected catalog suggestion is retained only as annotation provenance, not as a true pin ID for that example. Examples are saved in the ignored local `detection_feedback.sqlite3` database as PNG crops with source video path, frame number, track ID, box coordinates, and an unverified rights status. The annotation JSON marks only direct user decisions as feedback; linked orange or suppressed boxes are not added as extra training examples. Existing confirmed boxes and one representative per legacy rejected track are imported when annotations load. Undo and redo update the stored examples. **Remove area** never teaches the detector that the area contains no pin; deleting a confirmed annotation removes its associated positive example.

**Not this pin** keeps the box and any pin-presence confirmation. It records the rejected ID/name, rectangle, frame, and image crop in a separate wrong-identity table, clears that name from matching boxes on the same track, and asks the catalog matcher for another suggestion while excluding that rejected identity. The review is saved in the annotation JSON and restored on load; undo and redo update its stored crop. It does not create a non-pin example. The current catalog matcher uses these exclusions for the reviewed track; the saved crop is available for future identity-model training, but there is no learned identity classifier yet.

Future desktop detections pass coarse proposals through a small nearest-neighbour feedback ranker built from pin/non-pin reviewed crops. It promotes proposals similar to confirmed pins and suppresses close matches to rejected candidates when no comparable positive example exists. The ranker is rebuilt after affected pin/non-pin reviews, undo, redo, or annotation import. The right pane's **Feedback model...** button explains this behavior and shows the saved and usable positive/negative counts alongside the saved wrong-identity count; the status bar shows those counts and the current revision. A crop with too little visual detail remains saved but cannot affect the current ranker. Console logs report each revision and, for each detection pass, how many proposals were suppressed or could not be scored.

**Add to training data** saves the current session annotations, compares direct pin/non-pin and wrong-identity reviews with the local feedback database, and extracts crops only for new or modified reviews. **None of these** creates one wrong-identity review for each distinct pin in the displayed menu page; those crops are saved immediately and included in the training status. For example, 40 pages of 15 distinct rejected pins produce 600 wrong-identity records. Deleted reviews are removed from the database without decoding frames. An unchanged session finishes immediately, without rebuilding the ranker. Progress and ETA reflect only crops that still need processing; the final status shows the total, wrong-identity count, and added, updated, and removed counts. Confirmed pin names and IDs are retained alongside crops for future identity-model training. The current ranker learns pin versus non-pin proposals and does not train a neural identity classifier; wrong-identity reviews currently exclude rejected IDs from suggestions on the tracked object. Inferred orange boxes and propagated copies of one rejection are not counted as independent examples.

The ranker cannot recover an object that the proposal stage never finds. **Detect Pins** and manual navigation to an unprocessed frame try a contrast-normalized fallback when the primary pass yields no candidates; the status bar reports primary and fallback counts or that no candidates were found. This fallback can also find backing-card artwork, so review the blue boxes. Negative feedback now suppresses moderately similar rejected crops as well as near-identical ones, while a stronger positive match protects a proposal. These changes have synthetic regression tests but have not been measured on representative collection footage. The local crops are not uploaded to Cloudflare or Pinpanion; confirm reuse rights before exporting them for model training.

## Mobile scanner

The mobile app is a TypeScript progressive web app (PWA) built for Cloudflare Workers Static Assets. Install Node.js 24 or newer, then from `mobile_web/` run:

```powershell
cd mobile_web
npm ci
npm run typecheck
npm test
npm run dev
```

Open the local URL printed by Wrangler (normally `http://127.0.0.1:8787/`). The app can use the live camera, take or choose a photo, or play a recorded video. It proposes candidate areas and tracks strongly matching areas between scanned frames. A user can tag or reject an area and add a pin to an on-device collection. The pin picker lists known Pinpanion pins immediately and lets users combine name/ID search with year, category, set, event, and group filters. Filter options and result counts narrow as selections are made. The library also has **Add from catalog**. If a pin is absent from Pinpanion, an expandable section can record it under a separate local ID. Frames and photos stay on the device; the scanner sends no media to Cloudflare or the Python service. The collection JSON export remains available.

The Cloudflare deployment has two separate Worker environments configured in `mobile_web/wrangler.jsonc`:

| Environment | Public URL | Worker name | Deploy command |
| --- | --- | --- | --- |
| Production | `https://id.pinpanion.com/` | `pinident-mobile` | `npm run deploy:prod` |
| Development | `https://id.dev.pinpanion.com/` | `pinident-mobile-dev` | `npm run deploy:dev` |

To publish, the `pinpanion.com` DNS zone must be active in the Cloudflare account used by Wrangler, and that account needs permission to deploy Workers and attach both custom domains. Authenticate Wrangler (`npx wrangler login`), then run `npm run deploy:dev` from `mobile_web/`. Open the dev URL, check that the app loads and `/catalog.json` returns the Pinpanion feed, and only then run `npm run deploy:prod`. The commands build `dist/` and deploy it with the small Cloudflare Worker in `worker.ts`. Cloudflare creates the custom-domain DNS records and TLS certificates when the domain attachment succeeds. If either hostname is already attached to another service or has a conflicting DNS record, resolve that in the Cloudflare account before deployment. Production has no `workers.dev` alias; the dev environment also gets a Cloudflare `workers.dev` preview URL.

`pinident.pages.dev` is a Cloudflare **Pages** project hostname and is not created by this Workers deployment. The requested `id.dev.pinpanion.com` development hostname is configured directly. A separate Pages deployment would be needed if that optional alias becomes useful. The optional Python preview on port 8765 serves the same catalog route after `npm run build`.

The Worker serves `/catalog.json` from the same [Pinpanion `pins.json` file](https://pinpanion.com/pins.json) used by the Windows catalog importer; it does not scan images. Production and dev are distinct browser origins, so their on-device collections and cached catalog data are separate. Export a collection if it needs to move between them.

On Android, first open the deployed HTTPS URL while connected, then use the browser's **Install app** or **Add to Home screen** action. The service worker caches the app shell. After that first successful load, the app can be opened and used for candidate detection, local tags, collections, and export without an internet connection. The first successful online fetch stores a parsed copy of the Pinpanion feed's pin IDs, names, and filter metadata in IndexedDB for offline browsing and selection. This cache is not a separate hand-maintained list of valid pins. If no catalog was cached, a local unknown-pin name still works offline and stays outside the known-pin catalog. Reference artwork is not bundled or guaranteed offline. Clearing browser site data can remove the cache and local library, so export important collections.

**Automatic identification of a specific pin is not yet available offline.** The current mobile detector finds possible objects, while users choose a valid identity from the filtered, cached catalog. A separate local placeholder is available for pins missing from the catalog. The desktop Python ORB matcher cannot run in this static app; offline automatic identification needs an evaluated browser-compatible model and distributable reference assets. Candidate detection is heuristic and has not been evaluated on real phone footage.

Pinpanion **collection write access is not connected yet**. The public `pins.json` feed supplies pin metadata and images, but does not document user login, collection IDs, or a supported write endpoint. Saved collections stay in that browser's local storage until an authorized Pinpanion integration is available. Local custom pin IDs (`local:<id>`) are distinct from Pinpanion IDs (`pinpanion:<id>`), so a future sync can distinguish them. Do not clear browser site data without exporting the library first.

## Tests

Install `requirements-dev.txt` to get pytest, then run:

```powershell
python -m pytest -q
```

Tests use synthetic images and GUI fixtures; they do not require the ignored local `images/` or `labels/` directories.

The mobile TypeScript app has unit tests for the library and on-device scanner:

```powershell
cd mobile_web
npm test
```
